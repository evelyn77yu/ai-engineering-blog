双 Agent 交替开发：规则文件、滚动评审与漂移治理

一个可视化硬件编程工具的前端，从搭框架到部署上线，全部由 Claude 和 Codex 两个 AI 交替完成。我负责定义产品、设计两者协作的规则，并在每次合并前做最终决定。前后一共 21 轮，这篇复盘讲这套流程最后稳定成什么样，以及它在哪些地方失效过。

我用 Claude 和 Codex 两个 AI 交替开发了一个可视化硬件编程工具，从搭框架到部署一共 21 轮。我负责定义产品、设计两者的协作规则，并在每次合并前把关。做法有三点：约定写进能被机械检查的规则文件；每轮针对 diff 做交叉评审，用固定格式记录；两个 AI 都能改代码和文档之后，单独做漂移对账，把分歧交给人判断。最大的收获是：两个模型意见一致，不代表它们是对的，最终决定权必须留给人。

背景

面向模块化传感器节点的积木式编程工具：编辑器生成 Arduino 代码，配实时拓扑图，以及一个能看到当前工作区的 AI 助手。

我做了什么

设计了两份规则文件、一份单文件滚动评审日志和一套漂移对账机制。我自己担任需求方和合并前的最终决策人，前后推进了 21 轮评审。

关键判断

规则必须能被机械检查；评审的对象是 diff，而不是代码快照；两个模型意见一致，不代表它们是对的。

结果

产品完成部署。流程沉淀成一套可以直接照搬的三文件模板，同时暴露出四个“规则文件自己腐化”的问题。

01先看产品：一个硬件编排编辑器

这是一个浏览器里的单页应用，用户可以用拼积木的方式，给一组通过串口连接的传感器节点编写行为程序。界面分三块：左侧是积木编辑器，中间是实时拓扑，右下角是 AI 助手。AI 助手回答问题时能看到当前的模式、在线节点、LED 状态和程序结构，所以它更像一个懂这个工作区的助教，而不是通用聊天机器人。

工程上一共分六层，依赖方向只允许自上而下：界面外壳、程序文档与命令总线（所有修改都通过命令完成，可撤销）、运行时（带可见执行光标的积木虚拟机）、AI 助手（流式输出，带上下文构建）、设备连接（串口与重连状态机）、本地持久化。这样分层是后面“规则能被机械检查”的前提：边界画清楚了，才有东西可以检查。

02为什么要两个 Agent

单 Agent 模式跑了几周之后，三个缺陷才慢慢显露出来：

生成与检查共用一个上下文

同一个模型先设计、再实现，实现中的每一处妥协它都能自圆其说，因为解释和设计出自同一套推理。

缺少交叉审查

所有检查都是自查。笔误能查出来，设计层面的偏差查不出来。

架构被实现带偏

实现遇到阻力时，模型会顺手放宽边界，因为它眼下最紧迫的目标是进度。几轮之后，架构文档和代码就对不上了。

这三个问题的根源都是一个 Agent 只有一个视角。我的解法是引入第二个模型，并且做了更关键的一步：约定写在文件里，而不是留在对话里。会话一结束，对话上下文就没了，文件会一直留在仓库中。

03工作流全景

04规则要能被机械检查

规则拆成两个文件：AGENTS.md 对所有 Agent、所有会话生效，写的是常驻约束，包括架构隔离、禁止事项和评审流程；CLAUDE.md 只给单个工具使用，写技术栈、关键文件索引和必读清单。拆开的理由是变更成本：前者是大家共同依赖的约束，后者只是某个工具的上下文，两者合在一起，改任何一边的上下文都得动所有人依赖的那份文件。

整套流程里我认为最有价值的一条经验是：

判断

在有 Agent 参与的项目里，一条无法被机械检查的规则，实际约束力接近于零。Agent 很擅长在“看起来符合”和“确实符合”之间含糊过去，而人不会逐行核对。

无效的规则无法判定
  • 代码要优雅
  • 模块要解耦
  • 保持良好的可扩展性
真正生效的规则搜一次就能判定
  1. 设备层不允许引用界面框架
  2. 运行时层不允许引用界面框架或状态库
  3. 类型层不允许引用任何模块

右边每一条，在对应目录里搜索一次 import 就能判定是否违反；左边的“模块要解耦”永远判断不了。这个区别看起来很小，但它决定了规则是真的在约束 Agent，还是只是一句口号。

05单文件滚动评审

21 轮评审记录全部写在同一个文件里，每一轮的结构都是固定的：

Review Round N · 固定六段每轮必填
  1. 背景：这一轮在做什么、为什么做
  2. 关键正确性问题：协议不匹配、崩溃、不安全的解析
  3. 设计与规格偏离：和规格或架构文档对不上的地方
  4. 架构风险：耦合过紧、抽象边界、扩展性
  5. 建议的修复：按优先级排列
  6. 明确推迟的事项：必须填写，不能留空

固定格式要解决的问题很具体：没有格式约束时，评审输出会变成散文，下一轮负责执行的那一方读不进去。“推迟事项”强制填写，是为了把“暂时不做”显式记下来，因为技术债通常就是这么丢的：过一段时间，没人记得当初为什么没做。

坚持用单文件、不按轮次拆分，原因在于 Agent 的读取习惯：它会平等对待你给它的所有材料。如果目录里有 21 个轮次文件，第 3 轮已经废弃的设计会被当成当前依据。所以我在文件顶部维护了一个摘要区，写当前状态、已定决策、未决问题和推迟项；历史轮次则明确降级为“只作为记录保留，不是权威依据”。

另外两条约束是踩坑踩出来的。第一，评审的对象是 diff，不是代码快照。早期直接在主干上改完再让 Codex 评审，它没有明确的评审对象，只能泛泛而谈；改成每轮开工作分支之后，评审才有了靶子，意见也能逐条对应到具体修改。第二，原始评审输出不能直接拿去实施。AI 的评审里有大量“可以考虑”级别的噪音，执行方直接照单全收，会去改一堆不重要的问题。所以中间必须加一道规范化：把意见压缩成“改什么、改哪个文件、验收标准是什么”。

0621 轮里，产品和流程一起演进

回头看，评审轮次的切分方式本身就是一种设计。AI 助手如果一轮做完，负责评审的一方面对的是一个上千行的 diff，只能给出泛泛的意见；拆成四轮之后，每一轮都有清晰的验收标准：这一轮只验证外壳能不能渲染消息，下一轮只验证流式代理有没有把密钥留在服务端，依此类推。

07真正的难点：双基线漂移

让我三次修改工作流定义的，是漂移。早期流程是单向流水线：Claude 写代码，Codex 评审，我定方向。问题在于，Codex 评审时发现文档和代码不一致，却没有修改权，只能等；Claude 实现时发现设计不成立，同样只能等。所以从第 7 轮开始改成了双向：

Claude 和 Codex 都改代码、都改文档，工作在同一套共享文档上。仓库里可能暂时存在两条活跃基线：可运行的代码基线，和文档描述的意图基线。

效率明显提高了，但同一轮记录里我也写下了代价：两个 Agent 都能改代码和文档，漂移就会更容易发生。自由度上去，一致性就下来，这是整套流程里最核心的一个权衡。

08给 AI 助手设计上下文：能力和成本怎么取舍

产品里的 AI 助手也是我做取舍最多的地方。它要“懂工作区”，就得把工作区状态发给模型。可工作区状态有很多档：模式、在线节点、LED 状态、程序结构、运行日志，甚至几秒钟的完整传感器原始数据流。发得越多，答得越准，也越贵。我按测试模型的公开价格，把几类典型提问的成本估了一遍：

结论是一个分层策略：默认发精简上下文（当前模式、节点、LED 状态、程序摘要、最近日志），只有当问题确实涉及传感器或调试时才按需追加，全量原始数据流默认不发。界面上保留完整的聊天历史，但不在每次请求时都把全部历史发给模型，因为那部分成本会随对话长度线性增长，后续可以用摘要来压缩。

我同时把这个功能“离生产还差什么”写成了清单：密钥目前只放在服务端，前端只调代理接口；但真正对外开放之前，还需要用户身份、按用户和按 IP 限流、输出长度上限、每次请求的用量与成本日志、以及一个能随时关掉 AI 调用的总开关。能演示和能上线是两件事，把两者之间的差距写清楚，本身就是交付的一部分。

09过程中暴露的四个问题

规范腐化

规则文件自己成了最不规范的文件

后期出现了两组内容基本重复的条款。追加规则时没有人对照已有条款，Agent 也不会主动指出重复。规则文件的去重必须专门安排时间去做。

指令漂移

过期条款没有清理

有条规则要求“Mock 模式必须始终可运行”，但这个功能在第 21 轮被整体删除了。常驻规则里躺着一条要求维护已删除功能的指令，这比代码和文档不一致更隐蔽。应对方法是给规则加上时间戳和失效条件。

编号冲突

评审轮次编号撞车

中途重置过一次编号，结果第 3、4、5 轮各出现了两次。结论是编号一旦启用就不再复用，要重新开始就换一个命名空间。

共享先验

两个 Agent 一致，不等于正确

有一次双方都认可某个设计，采纳后才发现它不满足需求。两个模型共享相似的先验，会一起出错。交叉评审能消除随机性错误，消除不了系统性偏差。

最后一条决定了人的位置：一致意见可以快速通过，分歧点才是真正需要人做决策的地方。最终决定权必须留在人手里，原因不是模型能力不够，而是两个模型会以相同的方式出错。

10可以照搬的最小版本

不需要一上来就写 415 行规则。最小可用的版本只要三个文件：

最小模板从 20 行开始
  • AGENTS.md：常驻规则。每条都要能被检查，并且写上什么时候失效
  • docs/handoff.md：滚动交接日志，顶部是当前状态、已定决策和待办
  • docs/drift.md：漂移对账，只在出现分歧时写

11小结

  1. 规则要能被机械检查，否则就等于没有规则。
  2. 评审要针对 diff，并且先规范化再实施，否则会退化成泛泛而谈。
  3. 两个 Agent 都有写权限时，漂移是必然的，只能靠每轮显式标注、单独对账来管住。
  4. 上下文按需分层，默认发精简状态。全量数据通常是数量级的成本跳变，带来的收益却很少。
  5. 最终决定权要始终留给人，因为两个模型可能以同样的方式出错。
