作品集 / 03 · Agent Harness

受约束的 Agent Harness 设计：让 LLM 进入需要签核的芯片验证流程

芯片功能验证通常要占到 SoC 开发周期的一半以上，而且它的每一项产物都必须能追溯、能签核。我为这个场景设计了一套受约束的 Agent Harness，也就是包在模型外面的那层运行框架：约束、工具、记录和评估都在这一层。我先调研了公开的研究方案，再提出五模块架构和分阶段路线；其中第一阶段，也就是验证计划的自动化闭环，已经落地。这篇整理的是其中可以公开的部分：设计取向和方法论。

我为芯片硅前验证设计了一套受约束的 Agent Harness。这个场景的产物必须可追溯、可签核，所以我把目标从“尽可能自主”换成了“尽可能可靠”：LLM 只决定下一步做什么，编译、仿真和校验交给确定性工具，关键节点由工程师审核。框架分五个模块、四个阶段推进，第一阶段的验证计划自动化闭环已经落地。评估上，我更看重工程师的接受率和修改率，而不是生成成功率。

背景

验证工作的产物层层引用，执行环境强依赖专业工具链，出错代价也很高：一个错误的检查器可能产生虚假的覆盖结论，直接带来签核风险。

我做了什么

对比了 4 个公开研究方案和主要 EDA 厂商的方向，提出“LLM 决策 + 工具执行 + 工程师审查”的五模块 Harness。第一阶段完成了验证计划的自动生成与同步闭环。

关键判断

把目标从“尽可能自主”换成“尽可能可靠”。能被精确描述的动作不交给 LLM，失败路径要在设计阶段就定下来。

结果

得到一套可以落地的设计方法：三层职责、决策路由、降级链、可分层归因的执行记录（Trace），以及以人工接受率为核心的评估口径。

01先选取向：自主优先，还是可靠优先

很多 Agent 项目失败，原因不在模型能力，而在目标设定。Demo 阶段的默认目标是“让 Agent 尽可能自主”；可一旦进入需要签核的工程流程，问题就变成了：在结果必须可追溯的流程里，怎样让 LLM 参与进来，又不引入不可控的风险？这两种目标导向的设计方向几乎完全相反：

自主优先可靠优先（本框架）
关键动作由谁执行LLM 直接生成确定性工具执行
出错怎么办让模型自我纠正有限重试 → 降级 → 人工
什么算成功任务完成任务完成，并且可追溯、可复现
人的角色出了问题再兜底关键节点的强制审查环节

02为什么验证领域尤其需要约束

产物结构

层层引用的工程产物

验证计划、设计代码、测试平台、仿真日志和覆盖率数据库之间，有层级关系、引用关系和语义关联。

执行环境

离不开专业工具链

编译器、仿真器、覆盖率工具、回归系统和企业模板承担的功能，靠生成文本替代不了。

错误代价

错一处，签核就有风险

测试、检查器或覆盖率解读里的一个错误，就可能造成虚假的覆盖结论和错误的归因。

LLM 擅长的是理解目标、组织上下文、选择工具和解释结果。所以我给这个框架定的核心目标，是把 LLM 嵌进一个可审计、可复现、可以持续改进的验证闭环，而不是比谁生成的验证代码更多。

六条工程准则

这套 Harness 不是把能力堆到一个模型身上，而是一组受工程规范约束的机制。动手设计之前，我先定了六条准则：

准则要解决什么在设计里怎么体现
确定性优先减少模型幻觉和错误传播关键操作由确定性工具执行，LLM 负责决策和解释
结构约束产物能被下游工具直接使用格式校验、接口规范、引用一致性检查
可审计能追溯，能支撑签核执行记录、工具日志、版本控制和修改历史
问题驱动不为了用 Agent 而用 Agent优先解决验证计划、测试、调试和覆盖率收敛这几个真实痛点
可评估能持续改进基准集、指标看板、人工验收统计
可控的人工介入工程师保留最终判断权里程碑节点强制审核，异常时升级给人

常见的 Agent 机制，各放在什么位置

机制作用在这套框架里的定位
规划任务分解贯穿全流程；分解得越细，人工审核越可控
工具调用核心执行编译、仿真、解析这些关键操作全部经由工具完成
ReAct动态调整根据实时日志和报错信息决定下一步
反思纠错结合执行记录，修正结构、编译或策略层面的错误
多 Agent协作只用于需要不同角色相互把关的高风险任务

两张表合起来，意思是语义理解放开，执行过程收紧。这样做短期内会降低系统的自主程度，但换来的是可以量化评估，也为以后安全地扩展能力留出了空间。

03地基：三层职责划分

划分的逻辑是把不确定性圈在模型层。反过来设计也是可以的：让 LLM 直接生成关键产出，再由人逐条复核。但那样人很快就被用成了人工流水线，系统又退回到自动化之前的样子。

04五模块框架与分阶段路线

框架沿着验证流程展开成五个模块，推进节奏是三个“先……再……”：先建立可信的结构，再扩展生成能力；先在本地把工具闭环跑通，再接入云端和 CI/CD；先做局部的测试生成，再去做覆盖率收敛。

05第一阶段：验证计划的自动化闭环

验证计划是整条流程的起点：它把需求拆成可验证的特性，再挂上对应的测试和覆盖点。原来维护它要靠人工对照需求文档和代码库，需求一变就得逐条同步。第一阶段要解决的就是这件事：

这一步看起来“不够智能”，却是有意为之的：先保证结构可信，生成能力才有地方落脚。如果验证计划本身是靠模型自由生成的，后面每一个模块都要先怀疑它的输入。

06下游模块的统一接入：工具接口规范

测试生成、仿真调试和覆盖率收敛三个模块走同一条接入路径：任务定义 → 工具封装 → 接入验收。每一个工具除了输入输出，还必须定义下面这些项。最容易被忽略的是错误类型：

接口规范 · 必填项接入前验收
  • 输入参数与输出字段
  • 错误类型（可枚举的分类）
  • 超时策略，以及是否允许重试
  • 产物路径与回滚方式
失败时返回什么结构化
  • 状态：失败
  • 错误类型：未定义的信号
  • 位置：哪个文件、第几行
  • 相关产物：编译日志
判断

不要把几千行原始日志直接扔给模型，而要返回带错误类型的结构化结果。工具的输出格式，实际上决定了 Agent 的决策精度。

M2 · 测试生成

先搭框架、先能编译

查询设计和测试平台的接口，生成序列、约束、检查器和覆盖框架；然后调用编译，按差异做局部修复。

M3 · 仿真调试

先归类，再建议

把报错、致命错误、断言和超时转成结构化事件，区分问题出在测试、验证环境还是设计本身。高风险的修复要人确认。

M4 · 覆盖率收敛

找原因，而不是数数字

提取未覆盖项，结合设计信息分析原因，再提出定向测试或约束调整。最终结果由仿真和覆盖率工具确认。

07决策路由与降级链

不要一上来就设计 Agent，先把流程拆开。拆成节点以后，每个节点归入四类路由之一；而失败路径要在设计阶段就写成逐级降级的链条：

判断

一句话的判断标准：能被精确描述的动作，就不该交给 LLM。把所有步骤不加区分地交给 Agent，是从演示走向生产时最常见的失败原因。

08执行记录与分层归因

结果出现异常时，不要笼统地说“模型能力不行”，归因要落到具体某一层：

归因层典型症状
模型推理计划本身不合理，任务分解的粒度不对
上下文注入关键信息没有传进去，或者传了过期的版本
工具实现接口有缺陷，返回值不符合接口约定
下游依赖外部系统超时，或者返回格式变了

能不能定位到具体哪一层出了问题，决定了运维的效率。健康度除了看成功率，还要盯平均执行步数和成本这两个非百分比指标。成功率没有降，步数却翻了一倍，通常意味着系统正在靠重试掩盖某个缺陷。

09评估：人工接受率比成功率可信

评估体系由三部分组成：基准集回归测试（任何改动之后先跑一遍固定样本，防止悄悄退化）、指标看板，以及人工接受情况的统计。最后这一项值得展开说：

判断

“生成成功率”是一个可以被优化出来的数字，“人工接受率”不是。系统可以把产出做得越来越完整，可如果工程师每次都要大改，它的实际价值是负的。

所以要同时统计四个指标：生成成功率、人工接受率、人工修改率、升级到人工的比例，四者组合起来才能反映真实的可用性。同理，提示词、工具、模板和模型的任何改动都应该触发回归。大多数 Agent 系统不是突然崩溃的，而是在一次次小改动里悄悄退化的。上线之后，还需要灰度发布和回滚能力作为最后一道保险。

10什么时候才拆 Multi-Agent

默认形态是“单 Agent + 工具闭环”，因为它更好控制、更好审计、也更好评估。只有出现客观的职责冲突信号时，才考虑拆分：

信号 1

执行链过长

单个 Agent 的上下文开始遗忘早期决策，分阶段总结也压不住。

信号 2

任务互相阻塞

生成和调试需要并行推进，串在一条链上会卡住。

信号 3

需要独立审查

高风险产出必须由“不是作者本人”的角色复核。

拆分时的纪律：沿用同一套工具层和执行记录机制，不要每个角色各建一套；角色之间的交接用结构化内容，不用自然语言转述；引入审查角色时，要能验证“审查是否真的发现了问题”，而不是走过场。Multi-Agent 解决的是职责冲突，不是任务复杂度。

11借鉴了什么

公开方案可借鉴的要点对应模块
AutoBench测试生成要同时包含激励、检查器和自动评估，而不能只生成激励M2
VerilogCoder规划 + 工具反馈 + 结构化观测 + 局部修复：从“一次生成”走向“观察、修正、再执行”M2 · M3
FVEval把验证能力拆成可度量的分层任务，界定能力边界M5

EDA 厂商公开方向验证空间优化、覆盖率收敛、调试辅助、部署形态M3 · M4 · 路线

12明确不下的结论

一份可信的设计文档，要说明自己没有得出哪些结论。这套框架只覆盖设计原则和机制，不对生成成功率、覆盖率提升、修复效果或效率收益下任何量化结论，这些都要靠模块级和端到端实验去验证。下一步要做的，是建立人工操作的基线，构建由资深验证工程师标注的基准集，并设计权限控制和安全沙箱，确保 Agent 生成的代码只有通过校验才能进入正式代码仓库。

边界

一个把所有指标都报得很好看的方案，通常意味着它还没有进过真实的生产环境。

13小结

  1. 可靠性不是模型问题，而是系统问题。约束、路由、降级、归因，都是在模型之外设计的。
  2. 能被精确描述的动作不交给 LLM。LLM 输出的是“下一步做什么”，结果由工具产出。
  3. 先让结构可信，再扩展生成能力；先跑通本地闭环，再接云端和 CI/CD。
  4. 工具的错误类型决定 Agent 的决策精度；失败路径在设计期确定，而不是在故障时即兴处理。
  5. 用人工接受率和修改率来评估，任何改动都先过回归；Multi-Agent 只用来解决职责冲突。
