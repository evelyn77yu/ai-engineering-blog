# 双 Agent 交替开发：规则文件、滚动评审与漂移治理

过去几个月，我在一个多模块前端项目（React 19 + TypeScript，六个职责分层的模块）里用 Claude Code 与 Codex 交替开发，两个模型都对仓库有写权限。这篇文章记录这套流程最终稳定下来的形态，以及过程中暴露出来的问题。

项目是公开的：**[agent-ui](https://github.com/evelyn77yu/agent-ui)**。文中引用的 `AGENTS.md`、`CLAUDE.md`、`docs/review-notes.md` 和漂移对账文档都在仓库里，可以直接对照阅读。仓库 README 里有架构分层图和这套工作流的示意图。

---

## 1. 起点：单 Agent 模式的三个具体缺陷

有三种缺陷是在用单 Agent 做了几周之后才显性化的。

**生成与检查共用同一个上下文。** 同一个模型先做架构设计、再写实现，它会持续持有自己的设计意图。结果是实现里所有妥协的地方，它都能给出自洽的解释——因为那个解释和当初的设计决策出自同一套推理。让写代码的一方检查自己写的代码，在工程上本来就是不成立的。

**缺少对抗性检查。** 单 Agent 模式下没有第二个视角，所有检查都是"自查"。自查能发现笔误和遗漏，发现不了设计层面的偏差。

**架构会被实现反向带偏。** 这一点最难察觉。架构文档要求模块保持隔离，但实现遇到阻力时，同一个模型会顺手把边界放宽一点——因为在它的上下文中，实现进度是更紧迫的目标。若干轮之后，架构文档和代码就不再对应了。

这三点的共同根源是：一个 Agent 只提供一个视角。所以后续的方案是引入两个模型，并且——这一步是关键——**用文件而不是对话来传递约定**。对话上下文会随会话结束而消失，文件不会。

## 2. 协作约定写成文件：两份而不是一份

常见做法是只写一份 `AGENTS.md`。我最后用了两份，因为它们服务的对象不同：

| 文件 | 适用对象 | 内容 | 规模 |
|---|---|---|---|
| `AGENTS.md` | 所有 Agent、所有会话 | 常驻约束：架构隔离铁律、禁止事项、评审流程与格式 | 415 行 |
| `CLAUDE.md` | Claude Code | 项目上下文：技术栈、关键文件索引、运行方式、动手前的必读清单 | 155 行 |

拆分的理由是变更成本：`AGENTS.md` 是共同约束，`CLAUDE.md` 是单个工具的上下文。合并成一份之后，调整某个工具的上下文就要改动所有人都依赖的文件。

`CLAUDE.md` 开头是一份阅读顺序清单，作用是让 Agent 在动手前先定位到权威文档，而不是靠推测：

```markdown
## Before You Do Anything
1. Read `AGENTS.md` — 所有常驻指令与架构隔离规则都在里面
2. 如果要碰串口或协议代码：先读 `reference/arduino/`（协议的唯一真相源）
3. 如果要碰 UI 布局：遵守 `docs/product-spec.md` 里已确认的布局
4. 如果要碰架构：查阅 `docs/architecture.md`
5. 如果要碰状态：所有文档变更走 CommandBus，不要直接 setState
```

### 规则要能被机械检查

这是这套流程里我认为最有用的一条经验。

无效的规则长这样：代码要优雅、模块要解耦、注意可维护性。这类规则没有任何判定标准，Agent 可以声称自己满足了，你也没法反驳。

`AGENTS.md` 里实际生效的规则是这种形式：

```markdown
## 9a. Architecture Isolation Rules

1. `device/` 不允许 import React。
   DeviceConnector 和 MockConnector 必须是纯 TypeScript。
2. `runtime/` 不允许 import React 或 Zustand。
   BlockVM 的所有依赖必须由构造函数或函数参数传入。
3. `store/` 不允许 import React。
4. `commands/` 不允许 import React。
5. `types/` 不允许 import 任何东西，只放类型定义。
```

区别在于可验证性。第 2 条规则只需要在 `device/` 目录下搜一次 `from 'react'` 就能判断是否违规；"模块要解耦"永远无法判断。

结论可以直接推广：**在有 Agent 参与的项目里，一条无法被机械检查的规则，实际约束力接近于零。** 原因是 Agent 很擅长在"看起来符合"和"确实符合"之间模糊过去，而人不会逐行核对。所以我把关键约束全部改写成了可检索的形式，评审时按清单逐条打勾。

同一节里还有几条来自踩坑的规则：

```markdown
- `effectAllowed` / `dropEffect` 规则：调色板拖拽用 'copy'，画布重排用 'move'，
  两者必须匹配。浏览器在两者不匹配时会静默拒绝 drop——不报错，只是什么都不发生。
- `e.stopPropagation()` 规则：所有拖拽事件处理器必须调用它。
  漏掉会导致重复的 drop 处理和错误的插入位置计算。
```

浏览器静默失败这种行为，只有踩过才知道。把它写进规则文件，下一个 Agent 就不需要再踩一次——这是把个人经验转成可继承约束的方式。

## 3. 评审日志：单文件滚动

评审记录最终累积到 21 轮，全部放在同一个文件 `docs/review-notes.md` 里，而不是每轮一个新文件。轮次格式是强制要求的：

```markdown
# Review Round N — <标题>

## Context                      # 这一轮在做什么、为什么
## Critical correctness issues  # 协议不匹配、运行时崩溃、不安全的解析
## Design/spec deviations       # 与产品规格或架构文档的偏离
## Architecture risks           # 紧耦合、抽象边界、扩展性隐患
## Suggested next-step fixes    # 按优先级排列的可执行修复
## Deferred items               # 明确推迟的事项
```

固定格式解决的是一个具体问题：没有格式约束时，评审输出会变成散文，下一轮的执行方读不进去。其中 `Deferred items` 是必须填写的——它强制把"暂时不做"显式记录下来，而不是让问题从记录里消失。技术债通常就是这样积累起来的：没有人记得当初为什么没做。

选择单文件而不是每轮一个文件，原因在 Agent 的读取行为上：**它会把提供的所有材料平等对待。** 如果目录里有 21 个轮次文件，第 3 轮里已经废弃的设计会被当成当前依据。所以我改成单文件滚动，并在顶部维护摘要区：

```markdown
# Review Notes
## Current State              # 当前实现是什么
## Resolved Decisions         # 已经定下来的决策
## Open Issues                # 还悬着的问题
## Deferred Items             # 明确推迟的
## Historical Review Rounds   # 下面是历史，不是第一真相源
```

历史轮次被明确降级为背景资料，文件里写得很直白：

> 下面这些章节只作为历史变更记录和审计上下文保留。它们不是第一真相源；上面的摘要区和主要产品/架构文档才是权威。

## 4. 评审输出需要经过规范化

工作流里有一条约束，实际作用比它看起来重要：

> Raw Codex output is not the final implementation input.
> 原始评审输出不是最终的实施输入，必须先规范化成简洁、可执行的工程语言。

原因是 AI 评审输出通常包含大量"可以考虑""建议关注"级别的条目，其中相当一部分是噪音。如果执行方直接消费原始输出，它会去修改一批不重要的问题，甚至动到不该动的模块。

所以在评审和执行之间必须有一道规范化工序：把原始输出压缩成"改什么、改哪个文件、验收标准是什么"。

同一条规则还覆盖另一个约束：

> 如果某个评审发现被有意推迟，评审记录里必须明确写出来。

这条把"已知但暂不处理"和"没有被看到"区分开了。前者是决策，后者是失误，在项目复盘时差别很大。

## 5. 评审对象是 diff，不是代码快照

早期流程是直接在主干上改，然后让 Codex 评审。问题很快出现：它没有评审对象。让它"评审一下代码"，它只能看当前快照，无法判断改了什么、为什么改，评审就退化成泛泛而谈。

改进后的流程：

```markdown
## 18. Branch-Based Review Workflow

- `main` 保持为稳定基线
- 每个「实现 / 评审」周期开一个专用工作分支
- Codex 的对抗性评审针对「工作分支相对于 main 的差异」进行
- 不要在 main 上依赖 `main...HEAD`
- 如果评审目标的 diff 为空，先创建工作分支并提交变更
- 每个周期用有名字的分支，例如：
  - feature/review-round-1
  - feature/ui-polish-round-2
  - feature/runtime-fixes-round-3
```

核心是把评审的输入从"代码"换成"变更"。有明确 diff 之后，评审才有靶子，输出也能逐条对应到具体的修改。

其中"不要在 main 上直接工作时依赖 `main...HEAD`"这条，是因为那时 diff 为空，评审会空转。这类细节只有实际跑过流程才会写进规则。

## 6. 主要难点：双基线漂移

前面几个机制都比较顺利。真正让我三次修改工作流定义的，是漂移问题。

### 第 7 轮的模型变更

早期模型是单向流水线：

- Claude Code 写代码
- Codex 做需求对齐评审
- 人决定下一轮改什么

实际使用中这个模型不够用。Codex 在评审时经常发现文档与代码不一致，但它只有评审权没有修改权，只能等待；Claude Code 在实现时也会发现文档里的设计不成立，同样只能等待。两边都在互相等。

所以第 7 轮把它改成了双向的，记录原文如下：

> **上一版隐含模型：**
> - Claude Code 写代码
> - Codex 评审需求对齐
> - 人提出下一步变更
>
> **当前批准的模型：**
> - Claude Code 和 Codex **都**修改代码
> - Claude Code 和 Codex **都**修改文档
> - 两个 Agent 工作在**同一套共享的产品文档**上
> - 仓库中可能**暂时存在两条活跃基线**：
>   - 当前可运行代码基线
>   - 当前文档意图基线

效率提升明显，但同一轮的记录里也写下了对应的风险：

> **架构风险：** 当两个 Agent 都能修改代码和文档时，**漂移会变得更容易**——除非每一轮都记录清楚"当前是代码领先还是文档领先"。

自由度提高之后一致性会下降，这是这套流程里最需要处理的权衡。

### 处理方式一：每轮标注哪一方领先

从第 7 轮起，每轮评审都要回答当前差异属于哪一类：

1. 文档领先代码
2. 代码领先文档
3. 两者都成立，需要人来裁决

第三类是需要保留的。有些分歧不是对错问题，而是两个方案都成立，只是需要人做决策。把它显式标记出来，比让 Agent 自行判断安全得多。

### 处理方式二：单独的漂移对账文档

评审轮次不足以覆盖这个问题，因为差异会散落在各轮记录里。所以另加一份文档，职责单一：记录代码基线与文档基线之间的当前分歧。

这份文档开头的定位说明比文档本身更重要：

> 这个文件的**目的不是判断哪一方自动正确**，而是**把差异显式化**，让下一轮实现可以有意地选择跟随哪一个基线。

如果目标是"裁决对错"，每次都要争论；实际目标是"列清单"，那就只需要机械对比。文档里另有一条操作规则，我在后续项目里一直沿用：

> 新的漂移应该这样处理：
> 1. 尽量在同一轮里同时更新代码和文档
> 2. 如果某一方有意先行，就在评审日志里追加新的一轮
> 3. 把这份文档当作**活的协调笔记，而不是冻结的审计报告**

## 7. 过程中暴露的四个问题

### 指令文件自身出现了重复条款

`AGENTS.md` 后期出现了这样的标题序列：

```
## 14. Review-Note Driven Iteration
## 15. Rolling Review-Note Workflow
## 16. Review-Note Round Format
## 19. Rolling Review-Notes File      ← 与第 15 节内容基本重复
## 20. Review Round Format            ← 与第 16 节内容基本重复
```

规范文件自己成了最不规范的文件。原因是追加规则时没有对照已有条款，而 Agent 不会主动指出"这和第 15 节重复"。结论是：规范文件的去重整理必须显式安排，它不会自己发生。

### 过期条款没有清理

`AGENTS.md` 第 4 节原本写着：

```markdown
## 4. Mock Mode Must Always Be Runnable
Mock mode 是默认且主要的演示模式，必须零硬件可运行。
永远不要为了做串口功能而破坏 mock mode。
```

这条规则在当时是合理的。但后来产品方向调整，mock mode 被整体删除，评审日志的当前状态区里明确记着 "Mock mode has been removed — serial-only"。于是这份 415 行的常驻文件里，第 4 节变成了一条要求 Agent 维护已删除功能的规则。

这是比代码-文档不一致更隐蔽的一类漂移：指令与行为不一致。Agent 每次读到第 4 节，都会尝试遵守一个已经废弃的要求。

应对方式是给规则加时间戳和失效条件，写成「平台方向（2026-04）：……」这种形式。`AGENTS.md` 大部分章节本来有这个习惯，只有第 4 节没跟上。

### 评审轮次编号撞车

中途调整过一次工作流并重新开始编号，结果文件里出现了重复编号：

```
# Review Round 3 — 当前 UI / 运行时 / 文档同步
# Review Round 3 — 块编辑器 UX 与拓扑视觉打磨 (2026-04-03)
# Review Round 4 — ...
# Review Round 4 — 当前 UI / 交互文档同步 (2026-04-10)
```

同一个编号出现两次，当 Agent 被要求"参考第 5 轮"时无法确定指向。结论是编号一旦启用就不要重置，确实需要重新开始时换命名空间（如 `Round A1`），不要复用数字。

### 两个 Agent 的一致意见不等于正确

有一次 Claude 和 Codex 对某个设计都表示认可，我直接采纳了，后来发现这个设计不满足实际需求。两个模型共享了同样的先验假设，所以一起错了。

交叉评审能消除随机性错误（一次疏忽、一次遗漏），消除不了系统性偏差（共同的错误认知）。

所以现在的处理原则是：一致意见可以快速通过，分歧需要认真看。**分歧点往往才是真正的设计决策点**，也是应该由人做判断的地方。

## 9. 可以照搬的最小版本

不需要一上来就写 415 行规范。最小可用版本是三个文件：

```
AGENTS.md            # 常驻规则（从 20 行开始）
docs/handoff.md      # 滚动交接日志（当前状态 + 已定决策 + 待办）
docs/drift.md        # 漂移对账（只在出现分歧时才写）
```

`AGENTS.md` 的最小模板：

```markdown
# AGENTS.md

## 1. 项目目标
（一句话，含"不做什么"）

## 2. 目录与职责边界
（目录树 + 一句话职责）
铁律：core/ 不允许 import adapters/

## 3. 接口契约
（可执行的形式，不要散文）

## 4. 禁止事项
- 不要新增依赖，除非在此登记
- 不要修改 tests/ 下已有用例
- 不要"顺便"重构未提及的模块

## 5. 验收标准
- [ ] 通过测试
- [ ] 未违反第 4 节
- [ ] 已在 docs/handoff.md 登记

## 6. 已知坑（持续追加）
- xxx 在不同版本间返回格式不一致，用 yyy 包一层
```

`docs/handoff.md` 的每轮记录格式：

```markdown
## 当前状态
## 已定决策
## 待办与推迟项
## 变更记录
| 时间 | 执行方 | 范围 | 内容 | 原因 | 交叉检查 |
```

这三个文件加起来不到一百行，覆盖协作中最基本的三个问题：约定是什么、现在到哪了、谁在什么时候改了什么。

## 小结

跑完这个项目，比较确定的有四点：

1. 规则要能被机械检查，否则等于没有规则。
2. 评审要针对 diff，否则会退化成泛泛而谈。
3. 两个 Agent 同时持有写权限时，漂移是必然的，只能通过每轮记录状态来控制。
4. 人的裁决位必须保留，原因不是模型能力不足，而是它们会以相同的方式出错。
