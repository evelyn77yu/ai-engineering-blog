# 我用两个 AI 写了一个项目：AGENTS.md、21 轮评审日志与一场关于「漂移」的持久战

> 一个人做一个多模块项目，最痛苦的不是写代码，是**没人 review**。
> 我的解法是让 Claude Code 和 Codex 交替上阵，互相评审。
> 但真正的难点不在"用两个模型"，而在**怎么让它们在几十轮迭代后不跑偏**。
> 这篇是我完整的工作流记录，包含踩过的四个坑。

---

## 一、起点：单 Agent 开发的三个瓶颈

最初我用单个 AI 助手开发，很快就撞到三堵墙。

**第一堵墙：上下文单点故障。**
同一个模型先设计架构、再写实现，它会记住自己的设计意图——于是实现里所有偷懒的地方，它都觉得合理。你问它"这里为什么这么写"，它能给你一个自洽的解释，但那可能只是在为已经写下的代码辩护。

**第二堵墙：没有对抗性检查。**
写代码的人不该是检查代码的人，这是工程常识。但单 Agent 模式下，生成和检查共用一个上下文，等于自己给自己判卷。

**第三堵墙：架构被实现悄悄带偏。**
最难察觉的一种。你希望架构保持清晰，但只要实现遇到麻烦，同一个模型就会顺手把架构改歪一点——因为它同时持有两个目标，而实现是更紧迫的那个。几轮下来，架构文档和实际代码就对不上了。

这三堵墙的根源是同一个：**一个 Agent 只有一个视角。**

所以我的方案是引入两个视角不同的模型，并且——这是关键——**用文件而不是对话来传递约定**。

最后这个项目跑下来，仓库里沉淀了三样东西：两份 Agent 配置文件、一份 21 轮的评审日志、一份漂移对账文档。

---

## 二、两份配置文件，而不是一份

很多人第一反应是"写一份 AGENTS.md 就够了"。我最后用了两份，因为它们服务的对象不同：

| 文件 | 服务对象 | 作用 | 实际规模 |
|---|---|---|---|
| `AGENTS.md` | 所有 Agent、所有会话 | 常驻指令：架构铁律、禁止事项、评审要求 | 415 行 |
| `CLAUDE.md` | Claude Code | 项目上下文：技术栈、关键文件、不可妥协项、运行方式 | 155 行 |

`CLAUDE.md` 开头就是一段"动手之前必须先读"的顺序清单：

```markdown
## Before You Do Anything
1. Read `AGENTS.md` — 所有常驻指令与架构隔离规则都在里面
2. 如果要碰串口或协议代码：先读 `reference/arduino/`（协议的唯一真相源）
3. 如果要碰 UI 布局：遵守 `docs/product-spec.md` 里已确认的布局
4. 如果要碰架构：查阅 `docs/architecture.md`
5. 如果要碰状态：所有文档变更走 CommandBus，不要直接 setState
```

**为什么要拆两份？** 因为职责不同。`AGENTS.md` 是"法律"，`CLAUDE.md` 是"岗前培训"。前者要求所有 Agent 都遵守，后者只对特定 Agent 生效。混在一起写，会导致每次改一个 Agent 的配置都要动所有人的规范——这是我试过之后才明白的。

### 一个反直觉的经验：规则要能被机器检查

这是我在这份文件里学到的最重要的一课。

**没用的规则长这样：**

> 代码要优雅、模块要解耦、注意可维护性。

这种规则写了等于没写。因为"优雅"和"解耦"没有判定标准，Agent 可以声称自己做到了，你也无法反驳。

**有用的规则长这样**（这是 `AGENTS.md` 里真实的一节）：

```markdown
## 9a. Architecture Isolation Rules

1. `device/` 不允许 import React。
   DeviceConnector 和 MockConnector 必须是纯 TypeScript。
2. `runtime/` 不允许 import React 或 Zustand。
   BlockVM 的所有依赖必须由构造函数或函数参数传入。
3. `store/` 不允许 import React。
4. `commands/` 不允许 import React。
5. `types/` 不允许 import 任何东西，只放类型定义。
```

差别在哪？**第二条规则可以被机械验证。** 你只要 grep 一下 `device/` 目录里有没有 `from 'react'`，就知道有没有违规。前一条规则永远无法验证。

这个经验可以推广成一句话：

> **一条规则如果无法被机械检查，那么在有 Agent 参与的项目里，它约等于不存在。**

因为这正是 Agent 的软肋——它们很擅长在"看起来像那么回事"和"确实做到了"之间糊弄过去，而你不可能逐行核对。所以我把所有关键约束都改写成了可 grep 的形式，评审时直接按清单打勾。

同一节里还有几条这种"看起来啰嗦但救过命"的规则：

```markdown
- `effectAllowed`/`dropEffect` 规则：调色板拖拽用 'copy'，画布重排用 'move'，
  两者必须匹配。浏览器在两者不匹配时会静默拒绝 drop——不报错，只是什么都不发生。
- `e.stopPropagation()` 规则：所有拖拽事件处理器必须调用它。
  漏掉会导致重复的 drop 处理和错误的插入位置计算。
```

**"浏览器会静默失败，不报错"**——这种知识是人踩坑踩出来的，写进规则里，Agent 就不用再踩一次。

## 三、21 轮评审日志：为什么是一份滚动文件

第二个关键设计是评审日志。最终这个文件里有 **21 个评审轮次**，全部堆在**同一个文件** `docs/review-notes.md` 里。

### 固定的轮次格式

每一轮都必须包含固定的七个部分：

```markdown
# Review Round N — <标题>

## Context              # 这一轮在做什么、为什么
## Critical correctness issues    # 协议不匹配、运行时崩溃、不安全的解析
## Design/spec deviations         # 与产品规格或架构文档的偏离
## Architecture risks             # 紧耦合、抽象边界问题、扩展性隐患
## Suggested next-step fixes      # 按优先级排列的可执行修复
## Deferred items                 # 明确推迟的事项（必须写，不能省略）
```

这个格式是强制的，写在 `AGENTS.md` 里。它解决了一个很实际的问题：**没有固定格式时，评审结果会变成一堆随意的散文，下一轮的 Agent 根本读不进去。**

尤其重要的是 **`Deferred items`** 这一节。它逼你**把"暂时不做"显式记录下来**，而不是假装问题不存在。很多技术债就是这么滚出来的——没人记得当初为什么没做。

### 为什么是滚动文件而不是每轮一个新文件

我一开始想的是每次评审建一个新文件，比如 `review-round-1.md`、`review-round-2.md`……很快就放弃了。

原因是：**新来的 Agent 需要的是"当前状态"，而不是"历史的全部"。** 21 个分散的文件没法回答"现在架构约束是什么"这个问题。

所以我改成单文件滚动，并且在文件顶部维护几个摘要区：

```markdown
# Review Notes
## Current State          # 当前实现是什么
## Resolved Decisions     # 已经定下来的决策
## Open Issues            # 还悬着的问题
## Deferred Items         # 明确推迟的
## Historical Review Rounds   # 下面是历史，不是第一真相源
```

**历史轮次被明确降级为"背景资料"，而不是"当前真相"。** 文件里写得很直白：

> 下面这些章节只作为历史变更记录和审计上下文保留。它们不是第一真相源；上面的摘要区和主要产品/架构文档才是权威。

这一条非常重要。因为 Agent 有个很麻烦的习惯：**它会把你给它的所有材料平等对待。** 如果你给它 21 轮历史，它会拿第 3 轮里早就废弃的设计当依据。所以必须显式告诉它"哪部分作废"。

## 四、原始评审输出不能直接执行

这是我在工作流里加的最重要的一条约束：

> **Raw Codex output is not the final implementation input.**
> 原始评审输出不是最终的实施输入，必须先规范化成简洁、可执行的工程语言。

为什么？

因为 AI 评审输出往往**又长又飘**——它会列出一堆"可以考虑""建议关注"的东西，其中一半是噪音。如果让执行方直接吃这个输出，它会去修一堆不重要的问题，甚至改动根本不该动的模块。

所以中间必须有一道**规范化**工序：把原始输出压缩成"要改什么、改哪个文件、验收标准是什么"。

同一条规则还包含了另一个约束，我觉得很实用：

> 如果某个评审发现被有意推迟，**评审记录里必须明确写出来**。

这条把"我知道但先不做"和"我根本没看到"区分开了。前者是决策，后者是失误。项目管理里这两者的区别很大。

## 五、没有 diff 就没有评审

第三个机制是分支化的评审流程。

早期的做法是直接在主干上改，然后让 Codex 评审。很快就发现一个问题：**它没有评审对象。** 你说"评审一下我的代码"，它只能看当前快照，无法判断你改了什么、为什么改。于是评审变成泛泛而谈。

改进后的流程写进了 `AGENTS.md`：

```markdown
## 18. Branch-Based Review Workflow

- `main` 保持为稳定基线
- 每个「实现 / 评审」周期开一个专用工作分支
- Codex 的对抗性评审针对「工作分支相对于 main 的差异」进行
- 不要在 main 上依赖 `main...HEAD`
- 如果评审目标的 diff 为空，先创建工作分支并提交变更
- 每个周期用有名字的分支，例如：
  - feature/review-round-1
  - feature/ui-polish-round-2
  - feature/runtime-fixes-round-3
```

**核心逻辑：评审的对象是"变更"，不是"代码"。** 有了明确的 diff，评审才有靶子。

`AGENTS.md` 里甚至有一条专门讲这个坑：**"不要在 main 上直接工作时依赖 `main...HEAD`"**——因为那时 diff 是空的，评审会变成空转。这种细节只有真跑过 workflow 的人才会写出来。

## 六、真正的硬仗：双基线漂移

前面四个机制都还算顺利。真正让我改了三次工作流定义的，是**漂移**。

### 转折点是第 7 轮

早期的模型很简单：

- Claude Code 写代码
- Codex 做需求对齐评审
- 人提出下一轮改什么

这是一个清晰的**单向流水线**：写 → 审 → 改。

但实际用下来，这个模型不够用。因为 Codex 在评审时经常发现"这里的文档和代码对不上"，而它只有评审权、没有修改权，只能干等。同时 Claude Code 在写实现时，也经常发现文档里的设计不成立，同样只能干等。

所以我把工作流改成了双向的。第 7 轮的记录原文是这样的：

> **上一版隐含模型：**
> - Claude Code 写代码
> - Codex 评审需求对齐
> - 人提出下一步变更
>
> **当前批准的模型：**
> - Claude Code 和 Codex **都**修改代码
> - Claude Code 和 Codex **都**修改文档
> - 两个 Agent 工作在**同一套共享的产品文档**上
> - 仓库中可能**暂时存在两条活跃基线**：
>   - 当前可运行代码基线
>   - 当前文档意图基线

这个改动带来了巨大的效率提升，但也埋了一个雷。同一轮的记录里写着：

> **架构风险：** 当两个 Agent 都能修改代码和文档时，**漂移会变得更容易**——除非每一轮都记录清楚"当前是代码领先还是文档领先"。

这句话是整个项目里我最有共鸣的一条。**自由度上去了，一致性就下来了。**

### 解法一：每轮必须标注"谁领先"

从第 7 轮开始，每轮评审都必须回答一个问题：当前这条差异属于哪一种？

1. 文档领先代码
2. 代码领先文档
3. 两条都成立，需要人来裁决

**第三条最重要。** 它承认了一个事实：有些分歧不是"谁错了"，而是两个方案都合理，只是需要人来做决策。把这种分歧显式标记出来，比让 Agent 自己猜要安全得多。

### 解法二：专门开一份漂移对账文档

光靠评审轮次还不够，因为差异会散落在各轮里。所以我又加了一份专门的文档，职责单一：**记录代码基线和文档基线之间的当前分歧。**

它的开头有一段话，我觉得写得比文档本身更有价值：

> 这个文件的**目的不是判断哪一方自动正确**，而是**把差异显式化**，让下一轮实现可以有意地选择跟随哪一个基线。

**"不是判断谁对，而是把差异显式化"**——这个定位让这份文档变得很有用。如果它的目标是"裁决对错"，那每次都要争论；而它的实际目标是"列清单"，那只需要机械对比。

文档里还有一条操作规则，我后来在所有项目里都沿用了：

> 新的漂移应该这样处理：
> 1. 尽量在同一轮里同时更新代码和文档
> 2. 如果某一方有意先行，就在评审日志里追加新的一轮
> 3. 把这份文档当作**活的协调笔记，而不是冻结的审计报告**

## 七、我踩过的四个坑

前面讲的是机制，这一节讲真实翻车现场。

### 坑一：指令文件自己长出了重复条款

`AGENTS.md` 写到后期，出现了这样一组标题：

```
## 14. Review-Note Driven Iteration
## 15. Rolling Review-Note Workflow
## 16. Review-Note Round Format
## 19. Rolling Review-Notes File      ← 和第 15 节几乎是同一件事
## 20. Review Round Format            ← 和第 16 节几乎是同一件事
```

**规范文件自己变成了最不规范的文件。**

原因不难理解：每次想补充一条规则，新写的条款和已有的条款发生了重叠，但没人（包括 Agent）会主动说"这和第 15 节重复了，应该合并"。

**教训：规范文件也需要定期的去重整理，而且这件事必须显式安排，不会自己发生。**

### 坑二：过期指令没人删

`AGENTS.md` 里有一条铁律：

```markdown
## 4. Mock Mode Must Always Be Runnable
Mock mode 是默认且主要的演示模式，必须零硬件可运行。
永远不要为了做串口功能而破坏 mock mode。
```

听起来很合理。但后来产品方向变了，**mock mode 被整个删掉了**——评审日志的当前状态区里明确写着「Mock mode has been removed — serial-only」。

**于是那份 415 行的常驻指令里，第 4 节变成了一条要求 Agent 维护一个不存在的功能的规则。**

这是更隐蔽的一种漂移：**不是代码和文档不一致，而是指令和行为不一致。** Agent 每次读到第 4 节，都会试图"遵守"一个已经废弃的要求。

**教训：给规则加日期和失效条件。** 我现在习惯写成「平台方向（2026-04）：……」这种形式——`AGENTS.md` 里其实已经有这个好习惯，只是第 4 节没跟上。

### 坑三：评审轮次编号撞车

因为中途调整过一次工作流，重新开始了一轮编号，结果文件里出现了：

```
# Review Round 3 — 当前 UI / 运行时 / 文档同步
# Review Round 3 — 块编辑器 UX 与拓扑视觉打磨 (2026-04-03)
# Review Round 4 — ...
# Review Round 4 — 当前 UI / 交互文档同步 (2026-04-10)
```

**同一个编号出现了两次。** 当 Agent 被要求"参考第 5 轮"时，它不知道该看哪个。

**教训：编号规则一旦启用就不能重置。** 如果确实要重新开始，就换一个命名空间（比如 `Round A1`），不要复用数字。

### 坑四：把两个 Agent 的一致意见当结论

这是最贵的一课。

有一次 Claude 和 Codex 对某个设计都表示认可，我直接采信了。后来发现这个设计根本不满足实际需求——**因为两个模型共享了同样的先验假设，所以一起错了。**

交叉评审能消除**随机性错误**（一个疏忽、一次遗漏），但消除不了**系统性偏差**（共同的错误认知）。

**所以我的结论是：AI 之间的一致意见可以快速通过，但 AI 之间的分歧要认真看。** 分歧点往往才是真正的设计决策点——那才是该由人来做判断的地方。

## 八、跑完这个项目，我总结出四句话

1. **规则要能被机械检查。** grep 得到的规则才有约束力，"要优雅"这种话等于没说。
2. **让评审对着 diff 说话。** 没有变更范围，评审就会退化成泛泛而谈。
3. **把"谁领先"显式写下来。** 双 Agent 会修改同一批文件时，漂移是必然的，唯一的解药是每轮记录状态。
4. **永远保留人的裁决位。** 不是因为 AI 不够强，而是因为它们会一起错。

## 九、可以直接抄走的最小版本

如果你也想试这套方法，别一上来就搞 415 行规范。**最小可用版本只需要三个文件：**

```
AGENTS.md            # 常驻规则（先从 20 行开始）
docs/handoff.md      # 滚动交接日志（当前状态 + 已定决策 + 待办）
docs/drift.md        # 漂移对账（只在出现分歧时才写）
```

`AGENTS.md` 的最小模板：

```markdown
# AGENTS.md

## 1. 项目目标
（一句话，含"不做什么"）

## 2. 目录与职责边界
（目录树 + 一句话职责）
铁律：core/ 不允许 import adapters/

## 3. 接口契约
（可执行的形式，不要散文）

## 4. 禁止事项
- 不要新增依赖，除非在此登记
- 不要修改 tests/ 下已有用例
- 不要"顺便"重构未提及的模块

## 5. 验收标准
- [ ] 通过测试
- [ ] 未违反第 4 节
- [ ] 已在 docs/handoff.md 登记

## 6. 已知坑（持续追加）
- xxx 在不同版本间返回格式不一致，用 yyy 包一层
```

`docs/handoff.md` 的每轮格式：

```markdown
## 当前状态
## 已定决策
## 待办与推迟项
## 变更记录
| 时间 | 执行方 | 范围 | 内容 | 原因 | 交叉检查 |
```

**这三个文件加起来不到一百行**，但它们解决的是协作里最根本的三个问题：**约定是什么、现在到哪了、谁在什么时候改了什么。**
