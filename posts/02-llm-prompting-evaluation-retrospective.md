# 模型一个字没改，只换了问法：一次 320 次调用的提示策略评测复盘

> 同一个模型、同一套题、同一天跑完，四种提示策略的准确率差了 5 个百分点。
> 但这篇文章真正想讲的不是"哪种提示更好"——40 道题的样本量根本支撑不了这种结论。
> 我想讲的是**怎么把一个评测做得经得起别人检查**，包括那些我做得不够好的地方。

---

## 一、为什么要费这么大劲做评测

起因很简单：我在做 LLM 应用开发时发现，**改动提示词之后，我没法回答"这次改动到底让系统变好了还是变坏了"这个问题。**

凭感觉是不行的。改提示词、换模型版本、调整上下文策略——每一次改动都像是往一个黑箱里投硬币。效果好的时候你觉得是自己的功劳，效果差的时候你归因于"模型今天状态不好"。

所以我用一个小型项目认真做了一次对照评测：**同一个模型（Kimi-K2.5），40 道推理题，四种提示策略，完整记录每一步。**

结果是四种策略的严格准确率分别是 92.5%、90.0%、95.0%、92.5%。

但这个数字本身不是重点。**重点是：这些结论是可被验证的、并且我明确知道它不能推广到哪里。**

---

## 二、评测设计：先解决"对比能不能成立"

评测最容易犯的错误不是算错数，而是**变量没控制住，导致对比根本不成立。**

所以我先把所有条件固定下来：

| 项目 | 设置 |
|---|---|
| 模型 | `Pro/moonshotai/Kimi-K2.5` |
| 接口 | SiliconFlow（OpenAI 兼容） |
| 数据集 | 40 题，四个类别各 10 题 |
| Direct / Zero-shot / Few-shot | 温度 0.0，每题一次请求 |
| Few-shot 示例 | 三个人工编写的固定已解示例 |
| Self-consistency | Zero-shot CoT 提示，温度 0.7，每题五次独立请求 |
| 投票规则 | 对严格归一化后的答案计数，平票时取最早出现的答案 |

**四类任务的设计有讲究**：算术应用题、末字母拼接、字母计数、逻辑排序。这四类覆盖了不同性质的推理——有的是数值计算，有的是字符串操作，有的是空间/顺序关系推理。这样才能看出"某种提示策略是否只对某一类任务有效"。

### 一个我不能回避的问题

上面这张表里有个隐患：**四种策略的温度和调用次数并不相同。**

- Direct / Zero-shot / Few-shot 用温度 0.0（贪心解码）
- Self-consistency 用温度 0.7 + 五次采样投票

这意味着**这不是一次"等计算成本"的比较**。Self-consistency 付出了五倍的调用次数，如果在同等成本下比较，它该被允许跑五次然后取最好的——那样它的表现会完全不同。

我在报告里明确写了这一点，而不是把它藏起来。**因为如果不在自己的文章里说清楚，审阅者只会得出"作者不懂"的结论。**

## 三、答案提取与归一化：为什么必须做两套评分

这一节看起来琐碎，但它可能是整个评测里**最容易产生偏差**的环节。

### 提取规则

优先取最后一个 `Final answer:` 后面的内容；如果没有，取最后一个非空行；然后清理部分标点。

为什么要定这么具体的规则？因为模型输出的格式是不稳定的。同一道题，它可能输出：

```
答案是 30
Final answer: 30
经过计算，得到结果：30 dollars
```

如果没有统一的提取规则，你的评分结果会混入大量"格式不匹配"造成的假失败——**而那些失败跟模型的推理能力毫无关系。**

### 严格评分 vs 宽松评分

我做了两套归一化：

- **严格**：转小写、合并空白、去掉末尾句号。这是主指标。
- **宽松**：额外处理部分单位、答案前缀、整数小数形式、括号说明和特定冠词。只作辅助参考。

一个真实案例说明了为什么需要两套：

> 题目问 Lena 的余额（25 − 7 + 12）。Few-shot CoT 给出 `30`，Direct Prompting 给出 `30 dollars`。
> **标准答案是 `30`。** 严格评分下 Direct 判错，宽松评分下判对。

如果只有严格评分，Direct Prompting 会因为"多说了个单位"而丢分——但这显然不是推理失败。

不过我也没有把宽松规则做成万能兜底。文档里明确写了它的边界：

> 宽松规则不是语义判断器。例如 `The museum opens first` 不会被自动改为 `museum`，在两种评分下均不匹配。

**宽松规则处理的是格式差异，不是语义差异。** 把这条线划清楚，可以避免"为了让结果好看而放宽标准"。

## 四、结果：数字与它背后的东西

### 总体准确率

| 提示策略 | 做法 | 严格准确率 | 宽松准确率 |
|---|---|---:|---:|
| Direct Prompting | 直接给答案 | 92.5%（37/40） | 97.5% |
| Zero-shot CoT | 要求逐步推理 | 90.0%（36/40） | 97.5% |
| **Few-shot CoT** | 先给三个已解示例 | **95.0%（38/40）** | **100.0%** |
| Self-consistency CoT | 生成五次推理并投票 | 92.5%（37/40） | 100.0% |

**第一个反直觉的发现：Zero-shot CoT 比直接作答还差。**
"让我们一步步思考"这句几乎被神化的提示词，在这个评测里没有带来任何提升，反而低了一点。这提醒我：**CoT 不是万能的，它对任务类型高度敏感。**

**第二个发现：Few-shot CoT 表现最好。** 而且它的提升是"给例子"带来的，不是"要求推理"带来的。这和第一个发现互为印证。

### 分类别看，差异比总体大得多

总体准确率只差 5 个百分点，但拆到类别上完全是另一幅图景：

| 任务类别 | Direct | Zero-shot CoT | Few-shot CoT | Self-consistency |
|---|---:|---:|---:|---:|
| 算术应用题 | 90% | 90% | **100%** | 90% |
| 末字母拼接 | 100% | 100% | 100% | 100% |
| 字母计数 | 90% | **100%** | **100%** | **100%** |
| **逻辑排序** | 90% | **70%** | **80%** | **80%** |

两个关键观察：

1. **逻辑排序是所有策略的集体短板**，分布从 70% 到 90%，策略间的差距（20 个百分点）远大于总体差距（5 个百分点）。**而且 CoT 在这个类别上反而更差**——Zero-shot CoT 直接掉到 70%。
2. **末字母拼接全部分数拉满**，没有任何区分度。后来发现是因为修正了标签之后这个类别变得太简单了——它实际上是**失效的评测题**，留着只会让总体分数虚高。

**这就是为什么要做分类别统计。** 只看总体，你会以为"四种策略差不多"；拆开看，你会发现某个类别的模型能力根本没被区分出来，而另一个类别才是真正的瓶颈。

### Self-consistency 的成本收益

五次采样投票，换来的是：比 Zero-shot CoT 多答对一题（36 → 37），比 Few-shot CoT **少答对一题**。

**多花五倍调用次数，结果不如一次 Few-shot。**

这个结论很重要，因为它直接对应工程决策——在真实系统里，**Self-consistency 只有在"单次推理方差很大、且题目难度高"时才值得用**。在这次的 40 题上，它的性价比是负的。

## 五、三处标签修正：最容易被忽略、但最影响可信度

评测做到一半，我发现了数据集本身的问题。

| 题号 | 原标签 | 修正标签 | 理由 |
|---|---|---|---|
| 15 | `pak` | `plk` | deep / neural / network 的末字母为 p / l / k |
| 16 | `lag` | `leg` | natural / language / processing 的末字母为 l / e / g |
| 20 | `noft` | `nft` | chain / of / thought 的末字母为 n / f / t |

**标准答案本身是错的。** 如果不修正，模型答对也会被判错。

我做了两件事：

1. **在仓库里保留修正前后的完整差异**（`data/label_corrections.json`），而不是悄悄改掉。
2. 在报告中说明这些修正经过课程确认。

> **为什么这一步很关键？** 因为修改评测集是一个危险动作——它可以用来美化结果。所以做这件事的时候，**唯一的自证清白方式就是把改动过程完整留痕，让人能自己判断这个改动是否合理。**

顺带一提，修正之后"末字母拼接"这个类别所有策略都变成 100%——这反而暴露了这批题太简单。**修完 bug 才发现题目本身没区分度，这也是评测里的常态。**

## 六、让结论可被验证：三个工程化设计

这部分是我最想分享的——**一个评测如果别人无法验证，那它的结论价值等于零。**

### 设计一：离线验证脚本，不需要 API Key

仓库里有一个 `verify_results.py`，任何人 clone 下来都能直接跑：

```bash
pip install -r requirements.txt
python scripts/verify_results.py
```

它不调用任何 API，只做一件事：**核查已归档结果的内部一致性**——原件哈希、题目覆盖、答案提取、评分标记、采样投票、汇总准确率。

这个设计解决了一个很实际的问题：**别人不会为了验证你的结论去申请 API Key、花自己的钱重跑实验。**

所以他们只需要检查你的数据处理逻辑对不对。真要重跑，另有入口。

### 设计二：CI 自动跑验证

配套的 GitHub Actions 在每次 push 和 PR 时自动执行：

```yaml
name: Verify archived evaluation
on: [push, pull_request, workflow_dispatch]
jobs:
  offline-verification:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
          cache: pip
      - run: pip install -r requirements.txt
      - run: python scripts/verify_results.py
```

**每次提交都自动确认"归档结果没有被意外改坏"。** 这在评测项目里尤其重要，因为很容易在整理文件时不小心动到结果。

### 设计三：重跑不覆盖，改动全留痕

- 重跑时脚本把原始实现和数据集**复制到新建的 `runs/<UTC时间>/` 目录**，避免覆盖历史结果。
- 文件来源用 `source_manifest.json` 记录，包含**文件大小和 SHA-256**。
- 从课程目录整理进仓库时，"只做改名与归类，报告、核心代码和历史结果内容未改写"。

**"未改写"这三个字必须能被检验，所以才有哈希清单。** 口头保证在工程里不算数。

### 还有一个细节：失败恢复

一次完整实验需要 **320 次模型请求**（40 题 × 4 策略，其中自洽性占 5 次），加上重试会更多，会产生实际费用。中途挂掉很常见。

所以脚本支持断点续跑：

```bash
RERUN_FAILED_ONLY=1 python runs/<your-run>/prompting_experiment.py
```

配合 `MAX_RETRIES=6`、`RATE_LIMIT_SLEEP_SECONDS=30` 的限流退避策略，一次跑不完可以接着跑，不用从头重来。

> **这里有个经验：任何会产生费用的长任务，都必须先设计"失败了怎么接着跑"。** 否则一次网络抖动就让你损失一次完整实验的成本。

## 七、我明确写下的局限性

这一节我认为比结果部分更重要。我在报告里列出了以下局限：

- **40 题下，每题对应总体准确率的 2.5 个百分点，分类别准确率的 10 个百分点。** 也就是说单题波动就会明显影响结论。
- **没有重复实验、显著性检验或置信区间。** 所以策略之间的差异（比如 92.5% vs 95%）**很可能不显著**。
- **不同策略的温度和调用次数不同，不能视为相同计算成本的比较。**
- 原始依赖锁文件、随机种子、提供方模型修订和 token 费用未完整记录。
- 模型服务更新与随机采样可能改变重跑结果。

**其中第二条是最要命的：** 40 题上，95% 和 92.5% 之间只差一题。**一题之差就宣称"Few-shot 更好"是站不住的。**

那为什么还要做这个评测？因为它的价值不在于得出"哪种提示更强"的结论，而在于：**验证了一整套评测工程的方法是可行的**——数据集构建、变量控制、双轨评分、投票机制、可验证性设计、失败恢复。

**方法论是可以复用的，结论不能。**

## 八、如果重做，我会改什么

按优先级：

1. **扩大样本量到至少 200 题**，并且做显著性检验。40 题只能做 exploratory 分析。
2. **让 Self-consistency 的对照组也跑五次取最好**，做成真正的等成本比较。否则它的表现被不公平地低估了。
3. **剔除没有区分度的类别**（比如修正后的末字母拼接），或者提高难度。满分类别除了虚高总体分数，没有任何信息量。
4. **固定随机种子并记录**，让重跑可比。
5. **把成本也作为指标记下来**——准确率除以调用次数，这才是工程上真正要做的决策依据。

---

## 九、三条可以带走的经验

1. **评测的第一道关不是算分，是控制变量。** 变量没控制住的评测，数字越精确越误导。
2. **让你的结论可被验证。** 离线验证脚本 + CI + 哈希清单，这三样加起来成本不高，但能让结论从"我说的"变成"你能查的"。
3. **主动写下局限性。** 你藏起来的那个弱点，审阅者一定会发现。自己说清楚，它是严谨；被别人指出来，它就是硬伤。
