作品集 / 02 · LLM 评测

提示策略对照评测的复盘：变量控制、双轨评分与可验证性

改了提示词之后，系统到底是变好了还是变差了？没有对照基线时，这个问题只能凭感觉回答。为了能回答它，我把一次评测从头到尾完整做了一遍：同一个模型，40 道推理题，四种提示策略，320 次调用，全程留痕。这篇不讨论哪种策略最好，讨论的是怎样让一次对比站得住。

我在同一个模型上，用 40 道推理题对比了四种提示策略，一共 320 次调用，全程留痕。重点不是给策略排名，而是让对比站得住：先固定变量，再用严格和宽松两套口径评分，逐题做错误归因。分项结果一度显示 CoT 在逻辑题上更差，核对后发现 8 处判错里有 7 处只是冠词差异。最后我写了不需要 API Key 的离线验证脚本，配合 CI 和哈希清单，让别人可以独立复核结论。

背景

一个课程项目。目标不是给提示策略排名，而是建立一套“改了之后能说清好坏”的评测流程。

我做了什么

固定变量，统一答案提取，设计严格与宽松两套评分口径，逐题做错误归因；另外写了一个免 API Key 的离线验证脚本，配合 CI 质量门禁和哈希清单。

关键判断

初看结论是“逻辑排序题上 CoT 反而更差”。逐条核对后发现，8 处判错里有 7 处只是冠词或括号的差别，这个结论主要是评分口径造成的假象。

结果

Few-shot CoT 的严格准确率最高，为 95%。但更有价值的产出是一套可以复用、别人不花钱就能验证的评测流程。

01先给结果

提示策略做法严格准确率宽松准确率API 调用
Direct直接给答案92.5%（37/40）97.5%40
Zero-shot CoT要求逐步推理90.0%（36/40）97.5%40
Few-shot CoT先给三个已解示例95.0%（38/40）100%40
Self-consistency五次推理后投票92.5%（37/40）100%200

总体只差 5 个百分点，而且 40 道题撑不起“哪种策略更好”这种结论，后面会专门讲原因。这次评测里比数字更值得写的，是下面几个工程动作。

02先解决“对比是否成立”

评测里最常见的错误不是算错分，而是变量没有控制住，对比本身就不成立。所以在跑数据之前，我先把固定什么、改变什么全部写了下来：

项目设置性质
模型与接口同一个模型（Kimi-K2.5），同一个接口固定
题目40 题，四类任务各 10 题：算术应用、末字母拼接、字母计数、逻辑排序固定
答案提取与评分四种策略共用同一套规则固定
提示方式Direct / Zero-shot CoT / Few-shot CoT / Self-consistency被测变量
解码设置前三种用温度 0 单次贪心解码；Self-consistency 用温度 0.7，每题采样 5 次后投票必须声明的差异

四类任务是有意挑得分散的：算术偏数值计算，末字母和字母计数是字符串操作，逻辑排序是顺序关系推理。任务类型足够分散，才能区分一个策略是“只对某一类有效”还是“整体有效”。

判断

四种策略的温度和调用次数并不相同，Self-consistency 多付出了五倍调用，所以这不是一次等成本比较。我把这一点主动写进了报告。评测报告如果不主动说明自己的口径，审阅者得出的结论会是“作者没意识到”，而不是“作者有意这样选”。

03评测流水线

04双轨评分：格式失败不等于推理失败

答案提取的规则必须写得很具体：优先取最后一个 Final answer: 之后的内容，没有的话取最后一个非空行，再去掉标点。因为模型的输出格式并不稳定，同一道题可能输出 30、Final answer: 30 或 30 dollars。没有统一规则的话，评分里会混进大量和推理能力无关的假失败。

严格口径 · 主指标

转小写、合并空白、去掉末尾句号

防止分数虚高。比如标准答案是 30，Direct 输出了 30 dollars，严格口径下判错。

宽松口径 · 辅助参考

额外处理单位、答案前缀、括号说明和冠词

用来识别哪些失败和推理无关。但它的边界是写死的：只处理格式差异，不处理语义差异。

宽松规则不能做成万能兜底。比如 The museum opens first 不会被自动改写成 museum。这条线划清楚了，就不会出现“为了让结果好看而放宽标准”的情况。

05分项结果推翻了总体结论

总体上只差 5 个百分点，但拆到每个类别里，差异就大得多了：

严格准确率算术应用末字母拼接字母计数逻辑排序
Direct90%100%90%90%
Zero-shot CoT90%100%100%70%
Few-shot CoT100%100%100%80%
Self-consistency90%100%100%80%

策略之间的差异几乎全部集中在逻辑排序这一类。初看的结论是“CoT 在逻辑排序上反而更差”，但这个结论要先排除评分口径的影响。我逐条核对了这一类所有被判错的回答：

所以更准确的表述是：逻辑排序上严格口径的差距，主要来自答案的表述差异，而不是推理能力的差异。这也是双轨评分必须同时看的原因：严格口径防止分数虚高，宽松口径用来识别哪些失败与推理无关，只看其中一个都会得出错误结论。

关于多数投票，还有一个反例。逻辑排序题上，Self-consistency 的五次采样大多非常集中，10 题里有 7 题五次答案完全一致。但答案集中不等于答案正确：有一题五次回答一模一样，答案仍然是错的。多数投票能压住随机误差，压不住系统性偏差，因为五次采样共享同一套先验，错也会一起错。

06三处标签修正：改评测集要留痕

评测进行到一半，我发现数据集本身有错：三道末字母拼接题的标准答案标错了（例如 pak 应该是 plk）。不修正的话，模型答对了也会被判错。

我没有直接改掉，而是把修正前后的完整差异单独存档，并在报告中说明修正经过了确认。修改评测集这个动作本身就可以被用来美化结果，唯一的自证方式是把改动过程完整留下来，让别人自己判断是否合理。修正之后，末字母拼接四种策略全部是 100%。这反而暴露出这批题太简单、没有区分度，属于失效的评测题。

07成本应该是核心指标

做 LLM 应用时，采样投票这类方法往往被当作“免费提升”。在这次实验里它并不免费：采样投票的收益要按任务类别拆开算，只在少数推理类任务上值得这个价钱。如果重做，我会把成本作为核心指标放进主表。

08让结论可以被别人验证

别人如果无法验证一次评测，它的结论价值就有限。下面四个设计成本都不高：

离线验证

不需要 API Key 的验证脚本

不调用任何 API，只核对归档结果的内部一致性：文件哈希、题目覆盖、答案提取、评分标记、投票与汇总是否自洽。没有人会为了验证你的结论自费重跑一遍，所以应该让别人只需要检查数据处理逻辑。

CI 质量门禁

每次提交自动跑同一个脚本

评测项目里，整理文件的时候最容易动到结果文件本身。CI 用来确认归档结果没有在整理过程中被意外改坏。

来源清单

重跑不覆盖，来源可核对

重跑结果写入独立的时间戳目录；每个文件的来源、大小和 SHA-256 都记入清单。“整理时没有改写任何数据”这类声明必须能被检验，口头保证不算证据。

失败恢复

先设计好失败后怎么继续

320 次请求中途中断是常事。脚本支持只重跑失败的请求，并配合限流退避。任何会产生费用的长任务，都应该先想清楚失败之后怎么接着跑。

09局限与重做清单

40 题的规模下，每一题对应总体准确率 2.5 个百分点、分项准确率 10 个百分点；没有做显著性检验，95% 和 92.5% 之间只差一题；策略之间的温度和调用次数不同，不构成等成本比较；依赖版本锁定和随机种子也没有完整记录。

边界

方法论可以复用，但这批数据上得出的具体结论不能迁移到别处。

如果重做，按优先级排：

  1. 样本扩大到 200 题以上，并做显著性检验；
  2. 为 Self-consistency 设一个等成本的对照组；
  3. 剔除或加难没有区分度的类别；
  4. 固定随机种子，锁定依赖版本；
  5. 把“准确率 ÷ 调用次数”作为主表里的核心指标。

10小结

  1. 评测的第一关是控制变量，而不是算分。变量没控制住，数字越精确越误导人。
  2. 严格和宽松两种口径要同时看：一个防止分数虚高，一个识别与推理无关的失败。
  3. 答案高度一致不代表答案正确。投票能抑制随机误差，抑制不了共享先验带来的系统性偏差。
  4. 让结论可以被验证。离线脚本、CI 和哈希清单的成本都不高，却能把结论从“我说的”变成“你能查的”。
  5. 主动写下局限。没写清楚的弱点，审阅者一定会发现；自己写清楚是严谨，被别人指出来就是硬伤。
