# 提示策略对照评测的复盘：变量控制、双轨评分与可验证性设计

去年我在做 LLM 应用开发时遇到一个具体问题：改动提示词之后，我无法回答"这次改动让系统变好了还是变差"。没有对照基线，每次调整都只能凭感觉归因——效果好归功于改动，效果差归咎于模型。

所以我用一个课程项目把评测流程完整做了一遍：同一模型（Kimi-K2.5）、40 道推理题、四种提示策略、320 次模型调用，全部过程留痕。

项目是公开的：**[llm-prompting-evaluation](https://github.com/evelyn77yu/llm-prompting-evaluation)**。仓库 README 顶部有一张汇总表，下面这张是同一组数据的完整版本，加了调用成本一列：

| 提示策略 | 做法 | 严格准确率 | 宽松准确率 | API 调用 |
|---|---|---:|---:|---:|
| Direct Prompting | 直接给答案 | 92.5%（37/40） | 97.5% | 40 |
| Zero-shot CoT | 要求逐步推理 | 90.0%（36/40） | 97.5% | 40 |
| Few-shot CoT | 先给三个已解示例 | 95.0%（38/40） | 100.0% | 40 |
| Self-consistency CoT | 五次推理投票 | 92.5%（37/40） | 100.0% | 200 |

四类任务的分项结果：

| 提示策略 | 算术应用题 | 末字母拼接 | 字母计数 | 逻辑排序 |
|---|---:|---:|---:|---:|
| Direct Prompting | 90% | 100% | 90% | 90% |
| Zero-shot CoT | 90% | 100% | 100% | 70% |
| Few-shot CoT | 100% | 100% | 100% | 80% |
| Self-consistency CoT | 90% | 100% | 100% | 80% |

这篇文章不讨论"哪种提示策略更好"——40 题的样本量支撑不了这种结论。我要记录的是这套评测在工程上是怎么组织的，以及哪些地方做得不够。

---

## 1. 先解决"对比是否成立"

评测最常见的错误不是算错分，而是变量没有控制住，导致对比本身不成立。所以在跑数据之前先把条件固定下来：

| 项目 | 设置 |
|---|---|
| 模型 | `Pro/moonshotai/Kimi-K2.5` |
| 接口 | SiliconFlow（OpenAI 兼容） |
| 数据集 | 40 题，四个类别各 10 题 |
| Direct / Zero-shot / Few-shot | 温度 0.0，每题一次请求 |
| Few-shot 示例 | 三个固定的人工已解示例 |
| Self-consistency | Zero-shot CoT 提示，温度 0.7，每题五次独立请求 |
| 投票规则 | 对严格归一化后的答案计数，平票取最早出现者 |

四类任务的选择是有意为之：算术应用题偏数值计算，末字母拼接与字母计数是字符串操作，逻辑排序是顺序关系推理。只有任务类型足够分散，才能判断"某策略只对某一类任务有效"还是"整体有效"。

这里有一个必须说明的问题：**四种策略的温度和调用次数并不相同。** Direct / Zero-shot / Few-shot 是温度 0.0 的单次贪心解码，Self-consistency 是温度 0.7 的五次采样投票。这意味着它不是一次等计算成本的比较。Self-consistency 付出了五倍调用，如果在同等预算下比较，它应该被允许跑五次取最好的结果——那样它的表现会不一样。

这一点写在报告里，没有回避。评测报告如果不主动说明自身的口径问题，审阅者的结论会是"作者没有意识到"，而不是"作者有意选择了这种对照"。

## 2. 答案提取与双轨评分

这一节看起来琐碎，但它是整条流程里最容易引入偏差的环节。

提取规则：优先取最后一个 `Final answer:` 之后的内容；没有则取最后一个非空行；再清理部分标点。

规则必须具体到这种程度，因为模型输出格式不稳定。同一道题可能出现：

```
答案是 30
Final answer: 30
经过计算，得到结果：30 dollars
```

没有统一提取规则，评分里会混入大量由格式差异造成的假失败，而这些失败与模型的推理能力无关。

归一化做了两套：

- **严格**：转小写、合并空白、去掉末尾句号。作为主指标。
- **宽松**：额外处理部分单位、答案前缀、整数小数形式、括号说明和特定冠词。作为辅助参考。

一个实际案例能说明为什么需要两套。题目问 Lena 的余额（25 − 7 + 12），Few-shot CoT 输出 `30`，Direct Prompting 输出 `30 dollars`。标准答案是 `30`。严格评分下 Direct 判错，宽松评分下判对。如果只有严格评分，Direct 会因为多写了一个单位而丢分，这不是推理失败。

但宽松规则没有做成万能兜底，边界写得很明确：

> 宽松规则不是语义判断器。例如 `The museum opens first` 不会被自动改为 `museum`，在两种评分下均不匹配。

宽松规则处理格式差异，不处理语义差异。这条线划清楚之后，就不会出现"为了让结果好看而放宽标准"的情况。

## 3. 结果分析

### 总体

总体上有三个观察：

第一，Zero-shot CoT 没有超过直接作答（90.0% vs 92.5%）。"Let's think step by step" 这类指令在这个评测里没有带来提升。这和任务类型有关——四类任务里，末字母拼接和字母计数基本不需要多步推理，拆解反而增加了出错环节。

第二，Few-shot CoT 得分最高，提升来自给出示例，而不是要求推理。这与上一条互相印证。

第三，Self-consistency 用五倍调用换来比 Zero-shot CoT 多答对一题，但比 Few-shot CoT 少答对一题。在这批题上它的性价比是负的。

### 分项，以及一个评分口径问题

总体只差 5 个百分点，拆到类别上差异大得多：逻辑排序是 70%–90%，其余三类基本持平。初看结论是"CoT 在逻辑排序上反而更差"。

但这个结论需要先排除评分口径的影响。逻辑排序的答案是短语（`blue book`、`the table`），模型经常输出带冠词或补充说明的形式，严格评分会把这些判成错误：

| 策略 | 逻辑排序 严格 | 逻辑排序 宽松 |
|---|---:|---:|
| Direct Prompting | 90% | 100% |
| Zero-shot CoT | 70% | 90% |
| Few-shot CoT | 80% | 100% |
| Self-consistency CoT | 80% | 100% |

具体到条目：逻辑排序这一类在严格口径下一共判错 8 次，其中 **7 次的差异只在冠词或括号补充**：

```
gold = 'blue book'           pred = 'the blue book'
gold = 'museum'              pred = 'the museum'
gold = 'the table'           pred = 'the table (and the lamp)'
```

换成宽松评分后这 7 处全部判对。剩下 1 处真实错误来自 Zero-shot CoT，与提示策略本身有关，不是格式问题。

所以更准确的表述是：**逻辑排序上严格口径的差距（70%–90%），主要来源是答案表述差异，而不是推理能力差异；排除格式影响后，四种策略的差距收窄到 90%–100%。** 原来的"CoT 在逻辑排序上更差"这个结论，很大程度上是评分口径造成的假象。

这也是为什么双轨评分必须同时看：严格口径保证不会因为放宽标准而虚高，宽松口径用来识别哪些失败其实与推理无关。只看其中一个，都会得到错误结论。

另一个观察来自末字母拼接：四种策略全部 100%，没有区分度。修正标签之后这一类变得过于简单，属于失效评测题，留在里面只会抬高总体分数。

### 关于多数投票的一个反例

Self-consistency 在逻辑排序上的五次采样大多非常集中，10 题里有 7 题是 5/5 一致。但集中不等于正确——同一类题里有一题五次回答完全一致，答案仍然是错的（`the blue book`，5/5，严格口径判错；宽松口径判对）。

而真正出现分票的三题（如 `{"the lamp": 1, "the table": 2, "the table (and the lamp)": 2}`），分票原因基本是表述差异而非推理分歧，投票机制在这里并没有起到它理论上该起的作用。

结论是：多数投票能抑制随机性误差，但抑制不了系统性偏差——五次采样共享同一套先验时，它们会一起错。这一点和双 Agent 交叉评审遇到的情况是同一种问题。

## 4. 三处标签修正

评测进行到一半，发现数据集本身的问题：

| 题号 | 原标签 | 修正标签 | 理由 |
|---|---|---|---|
| 15 | `pak` | `plk` | deep / neural / network 的末字母为 p / l / k |
| 16 | `lag` | `leg` | natural / language / processing 的末字母为 l / e / g |
| 20 | `noft` | `nft` | chain / of / thought 的末字母为 n / f / t |

标准答案本身是错的。不修正的话，模型答对也会被判错。

处理方式是：修正前后的完整差异保留在仓库的 `data/label_corrections.json` 里，而不是直接改掉；报告中说明这些修正经过课程确认。

修改评测集是一个需要谨慎对待的动作，因为它也可以被用来美化结果。在这种情况下，唯一可行的自证方式是把改动过程完整留痕，让别人能自己判断改动是否合理。

修正之后，末字母拼接类别四种策略全部变成 100%——这反而暴露了这批题难度不足。修完数据问题才发现题目本身没有区分度，这在评测里是常见情况。

## 5. 可验证性设计

一个评测如果别人无法验证，它的结论价值就有限。这部分是我在这类项目里投入最多的地方。

**离线验证脚本，不需要 API Key。**

```bash
pip install -r requirements.txt
python scripts/verify_results.py
```

脚本不调用任何 API，只核查归档结果的内部一致性：文件哈希、题目覆盖、答案提取、评分标记、投票结果、汇总准确率。

这个设计解决的是一个很实际的问题：别人不会为了验证你的结论去申请 API Key、自费重跑实验。所以应该让他们只需要检查数据处理逻辑。真要重跑另有入口。

**CI 自动执行验证。** 配套的 GitHub Actions 在每次 push 和 PR 时运行同一个脚本：

```yaml
name: Verify archived evaluation
on: [push, pull_request, workflow_dispatch]
jobs:
  offline-verification:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
          cache: pip
      - run: pip install -r requirements.txt
      - run: python scripts/verify_results.py
```

每次提交都确认"归档结果没有被意外改坏"。评测项目里这一点尤其必要，因为整理文件时很容易动到结果文件。

**重跑不覆盖，来源可核对。** 重跑时把原始实现与数据集复制到新建的 `runs/<UTC 时间>/` 目录，不覆盖历史结果；文件来源记在 `source_manifest.json` 中，包含文件大小与 SHA-256。从课程目录整理进仓库时只做改名与归类，报告、核心代码和历史结果未改写——"未改写"这个声明需要可检验，所以才有哈希清单。口头保证在工程里不算证据。

**失败恢复。** 一次完整实验需要 320 次模型请求，加中途重试会更多，产生实际费用，中断很常见。脚本支持断点续跑：

```bash
RERUN_FAILED_ONLY=1 python runs/<your-run>/prompting_experiment.py
```

配合 `MAX_RETRIES=6` 与 `RATE_LIMIT_SLEEP_SECONDS=30` 的限流退避。任何会产生费用的长任务，都应该先设计好失败后如何继续，否则一次网络抖动就要重跑整轮。

## 6. 明确记录的局限性

这部分在报告里写在结果之后，但我认为比结果部分更重要。

- 40 题的规模下，每题对应总体准确率 2.5 个百分点、分项准确率 10 个百分点，单题波动就会明显影响结论。
- 没有重复实验、显著性检验或置信区间。策略之间的差异（如 92.5% 与 95%）很可能不显著。
- 不同策略的温度与调用次数不同，不属于等计算成本比较。
- 依赖锁文件、随机种子、服务方模型修订与 token 费用未完整记录。
- 模型服务更新与随机采样可能改变重跑结果。

其中第二条影响最大：40 题上，95% 与 92.5% 之间只差一题。凭一题之差宣称"Few-shot 更好"是不成立的。

那为什么这个项目仍然有价值？因为它验证的是一套评测工程流程的可行性——数据集构建、变量控制、双轨评分、投票机制、可验证性设计、失败恢复。方法论可以复用，具体结论不能迁移。

## 7. 如果重做

按优先级排列：

1. 样本量扩到至少 200 题并做显著性检验。40 题只适合探索性分析。
2. 为 Self-consistency 设置等成本对照组（其他策略也跑五次取最好），否则它的表现被系统性低估。
3. 剔除或加难度那些没有区分度的类别。满分类别只会虚高总体分数。
4. 固定并记录随机种子，让重跑结果可比。
5. 把成本作为一等指标记录——准确率除以调用次数，这才是工程决策真正需要的口径。

---

## 小结

三点比较确定的经验：

1. 评测的第一道关是控制变量，不是算分。变量没控制住，数字越精确越误导。
2. 让结论可被验证。离线验证脚本、CI、哈希清单三样东西成本都不高，但能把结论从"我说的"变成"你能查的"。
3. 主动写下局限性。没有写清楚的弱点，审阅者一定会发现；自己写清楚是严谨，被别人指出来是硬伤。
