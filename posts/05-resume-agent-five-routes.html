作品集 / 05 · Agent 应用

同一个求职问题的五种 AI 解法：从一份 Skill 到完整的 Agent 工作台

秋招要投几十个岗位，每个岗位都需要一份贴合 JD、又绝对真实的简历。这个问题我前后用五种方式解过：把经验写成 Skill 交给编码 Agent，让 HTML 页面直接调用本地脚本，在浏览器里搭一个分步确认的投递工作台，借用开源的多 Agent 求职系统，以及从零做一个完整的 Agent 应用。这五种方式不是谁淘汰谁，而是各自对应不同的场景、成本和风险。

为了秋招定制简历，我先后试了五种 AI 方案：把经验写成 Skill 交给编码 Agent，让 HTML 页面直接调用本地脚本，在浏览器里搭一个分步确认的投递工作台，借用开源系统做岗位评分，以及自己做一个完整的 Agent 应用。完整应用覆盖从岗位搜集到投递记录的 12 个环节，包括本地知识库检索、事实确认、多版本候选和 Agent 控制台。我的选型方法是：先看有没有不可逆的动作，再看需不需要沉淀状态，最后看规则是否稳定。

背景

海投场景：中英文都要，方向从 Agent、AI 平台、AI 产品一直到半导体，还要能被招聘系统正确解析。最大的风险是 AI 编造经历。

我做了什么

用五种路线覆盖了从岗位搜集到投递记录的 12 个环节。其中完整应用从产品规格开始，迭代了三个版本：本地 RAG 原型、可部署版、Agent 工作台。

关键判断

不是每个问题都需要一个 Agent 产品。规则稳定又高频，用 Skill 或脚本；需要跨次沉淀状态，才做应用；涉及外部账号和不可逆动作，必须分步确认。

结果

实际产出了数十份中英文岗位定制简历。真实性靠四道机制来保证：事实库、待确认环节、来源引用和真实性自查。

01问题：一份“好简历”的验收标准

在动手之前，我先把“好”写成了可以验收的标准。这一步决定了后面每条路线该怎么取舍：

验收标准来自产品规格
  • 真实：不生成没做过的项目，不补写素材里没有的数字；没有确认过的技能不能写进简历
  • 贴合：根据 JD 的关键词和岗位方向调整顺序与表述；中文强调业务场景和落地，英文强调 ownership、impact 和关键词，两种语言分别生成，不逐句翻译
  • 可解析：结构清晰，能被招聘系统和 AI 筛选系统正确识别
  • 版式：A4，通常两页；两页是排版目标，而不是删内容的理由
  • 省时：每份通常只改 2 到 4 处内容、1 到 2 处排版，人工环节控制在 30 秒到 1 分钟

最后一条很关键。它说明系统的目标不是替我做决定，而是把“找素材、写候选、排版”这些重复劳动压缩掉，把选择权和最终确认留给我。

02全流程，以及五种路线各管哪一段

03路线 A：把经验写成 Skill，交给编码 Agent

最轻的一种做法：不写任何应用，把我反复对 AI 说的要求整理成一份 Skill 文件，让本地的编码 Agent（Claude Code 或 Codex）每次改简历时自动加载。它本质上是把对话里的隐性经验变成显式规则：

内容规则节选
  • 从 JD 的职责和要求里提取 6 到 10 个高信号关键词
  • 围绕关键词改写角色行、个人简介、技能和项目要点
  • 按岗位类型套用不同的项目表述角度：Agent 类、产品类、硬件评测类
  • 红线：素材里没有的技术和经历，一律不写
工程规则节选
  • 新 JD 一律新建文件，从不覆盖已有版本
  • 沿用固定的 HTML 结构和 A4 打印样式
  • 命名规则固定，HTML 与 PDF 同名配对
  • 用无头浏览器导出 PDF，导出后核对文件确实存在

优点是几乎零成本，而且非常灵活。缺点同样明显：状态不会沉淀。哪些事实确认过、哪种表述我更喜欢、哪份投了哪家，每次对话都要重新理解一遍。这正是后面两条路线要补上的东西。

04路线 B：HTML 就是编辑器，按钮直接调本地脚本

很多时候，简历已经基本成型，我只想在页面上直接改几个字、保存，再一键生成英文版。为此我做了一个本地助手，让简历 HTML 页面上多出两个按钮：

这条路线里我最满意的一个设计是结构检查：英文结果的条目数、模块数和链接数必须与中文版一致，否则一个字都不写回。LLM 翻译偶尔会合并或丢掉条目，这个检查能用最低的成本把这类错误挡在文件之外。

05路线 C：浏览器里的投递工作台，每一步都要确认

投递沟通发生在招聘平台的聊天页里：读招聘方的消息、回复、发简历附件。这一步动的是真实账号，发出去的消息也收不回来，所以我把它设计成一个以页面内容为准、每个不可逆动作之前都要人工确认的工作流，跑在编码 Agent 自带的浏览器里：

发简历附件是风险最高的一步，所以单独设了一条边界：只有在我明确确认“公司、岗位、PDF 文件、发送话术”这四项之后，Agent 才会上传附件并发送，而且只删除本次上传的那一份附件，无法唯一识别时就不删。本地只保存轻量的索引：文件路径、状态和最近一次摘要，不保存完整的聊天记录。

判断

这一步交给 Agent 的价值不在“自动化”，而在于它不会疲劳，也不会跳步。人在处理第二十个对话时最容易犯的错，比如发错附件、回错人，恰好就是固定流程最擅长挡住的。

06路线 D：岗位发现与评分，直接用开源系统

岗位搜集和初筛我没有自己造轮子，直接用了开源的多 Agent 求职系统 career-ops：它能扫描招聘页面，按 10 个加权维度给岗位打 A 到 F 的分，再把结果写进一张投递追踪表。它的一条原则我很认同：低于 4.0/5 的岗位不推荐投递，它是一个过滤器，而不是海投工具。我自己记录的已投岗位，评分大多集中在 4.1 到 4.6 之间。

它的局限在于评分维度是通用的，并不了解我已经确认过哪些事实。所以我在自己的应用里给“职位发现”只留了一个入口和数据接口：将来单向读取它的评分结果和投递状态，而不是在它的基础上再造一套。

07路线 E：完整的 Agent 应用

前四条路线各自解决了一段问题，但有三件事只有一个真正的应用才能做好：跨次沉淀事实（哪些经历确认过、哪些技能可以写）、沉淀偏好（我总是选哪种表述），以及可追溯的版本（哪份简历投给了哪个岗位）。

三个版本，每次只回答一个问题

版本要回答的问题关键设计
v0 · 本地原型RAG 加多版本生成这条链路能不能跑通？前后端分离；本地知识库自动监听，按哈希增量索引；本地向量检索；支持多家模型；生成进度实时推送；拖拽配置后导出 HTML/PDF
产品规格它到底该做成什么样？先写需求，再写代码：验收标准、真实性原则、人工最终控制、信息架构、三层素材体系（事实库、表述库、历史版本库）
v1 · 可部署版能不能放到云端用？模型只在服务端调用，密钥不进浏览器；导入接口拒绝原始文件，只接受人工整理过的事实摘要
v2 · Agent 工作台怎样又真实、又省时？回到本地优先；事实确认环节；每条经历生成多个角度的候选，附推荐分和依据；Agent 控制台；快照和投递记录

v1 到 v2 的转向值得说一下：为了能部署到云端，v1 只允许导入手工整理的事实摘要，安全性很好，但往里面喂素材太费劲，日常根本用不起来。v2 回到了本地优先、单用户的定位，数据库也换成了单文件。知识库只有十几份文档，向量也直接存在同一个数据库里，检索用暴力计算余弦相似度，不再引入单独的向量数据库。基础设施的规模应该跟着数据规模走，而不是跟着技术热度走。

事实确认：先问清楚，再生成

JD 解析完之后，系统不会马上开始写，而是先把“素材里没有证据、但 JD 很看重”的东西变成一组需要我回答的问题。这些问题分三类：

新技能

JD 要的技能，素材里没有

问我用到了什么程度、在什么场景下用过、能不能接受面试追问。在我回答之前，这项技能不会被写进去。

冲突

两份素材说法不一致

比如时间、职责或者项目名称对不上，由我选择以哪一份为准。

指标

要不要写数字

素材里没有的量化指标绝不补写；有数字但还没确认过的，先问我。

工作台：多个候选、推荐分和依据

每个候选版本都附带一段“真实性核查说明”，写明这个版本没有引入素材之外的指标或职责。这些候选被选中或拒绝的次数会记进表述素材库，作为以后沉淀偏好的依据。这部分的数据结构已经就位，学习策略还在迭代。

Agent 控制台：一句话驱动整个工作台

工作台底部有一个常驻的 Agent 控制台，以指令栏的形式出现，可以直接说“密度调紧一点”“这条为什么排第一”“帮我查一下还缺 JD 里的哪些关键词”。它背后是真正的工具调用，而不是关键词匹配：

路线最适合的场景主要收益搭建成本可控与可复现主要短板
A · Skill规则稳定、频率高、一个人用经验沉淀成规则，改一份简历只需要一句话很低：一份规则文件中：取决于对话质量状态不沉淀，每次都要重新理解上下文

D · 开源系统岗位多，需要先筛一遍不重复造轮子，快速筛掉不值得投的岗位低：配置为主中评分维度通用，不了解个人事实库
E · 完整应用需要沉淀事实、偏好、版本和记录事实、偏好、版本和记录可以长期积累、反复使用高：前后端加数据模型最高：事实确认、来源引用、快照建设和维护成本最高

09选型三问

回头看，决定用哪条路线的其实就是三个问题，而且要按这个顺序问：

第一问

涉及外部账号或不可逆的动作吗？

涉及的话，无论用什么技术，都必须分步确认、回读核对，异常时立即停下交还给人。这一条优先级最高。

第二问

需要跨次沉淀状态吗？

事实、偏好、版本、记录，只要其中一样需要长期保存、可以比较，就值得做一个应用，并给它一个唯一可信来源。

第三问

规则稳定、使用频繁吗？

是的话，写成 Skill 或脚本就够了；如果还在探索阶段，就直接对话，不要过早地产品化。

判断

Agent 应用是这五种里最“像作品”的一个，但它不是默认答案。技术选型应该从场景、风险和成本出发，而不是从“能不能做成 Agent”出发。五条路线并存，恰恰是这个判断的结果。

10贯穿五条路线的一条红线：真实性

简历是 AI 最容易“好心办坏事”的地方：它很乐意帮你补一个看起来合理的数字，或者加一个 JD 里写了、你却没真正用过的技术。所以每条路线都有对应的防线：

事实库

只从已确认的事实出发

原始资料先被提取成一条条原子事实，确认过的才能在生成时被引用。

事实确认

没证据就先问

新技能、冲突、指标三类问题，回答之前都会阻断生成。

来源引用

每个版本都说明依据

标出引用了哪些事实、哪些检索片段，附相似度，并写一段真实性核查说明。

自查

导出前再查一遍夸大

在 Agent 控制台里可以随时调用真实性自查工具，逐条检查有没有无依据的数字和职责。

11小结

  1. 同一个问题可以有很多种 AI 解法。先把验收标准写清楚，再去比较哪种解法最划算。
  2. LLM 只放在真正需要它的那一步。备份、结构检查、页数检查、导出，全部交给确定性的脚本。
  3. 涉及外部账号和不可逆动作时，分步确认、回读核对、异常即停，比任何“智能”都重要。
  4. 做完整应用的理由，是需要沉淀状态；基础设施的规模应该跟着数据规模走。
  5. 真实性是红线，要用机制去保证：事实库、事实确认、来源引用、自查，而不是靠一句“请不要编造”。
